## Prioritized improvements

### P0 — complete these before a production rollout

1. **Repair the backend test suite after deleting the old verification service.** `functions/tests/verification_service.test.ts:5` still imports deleted `functions/src/verification/verificationService.ts`, so Jest cannot compile that suite. Replace obsolete automatic-approval expectations with tests of the current manual-review callables, ownership, state transitions, scanner gate and registry allowlist. Preserve platform-default test coverage. Do not restore fabricated approvals just to pass tests.
2. **Read applicants from the actual application collection.** `HospitalRepository.getApplicationsForDuty` queries `assignments` with `applied`/`shortlisted` statuses. `applyToDuty` writes `duties/{dutyId}/applications/{doctorId}` with `submitted`/`shortlisted`; assignments exist only after selection. Use the scoped application collection and existing snapshots, then exercise hospital review and selection under real rules. Reading from assignments also lacks the organization constraint needed by the tenant read rule.
3. **Send the confirmation contract correctly.** `DoctorRepository.confirmAssignment` sends only `assignmentId`; `ConfirmAssignmentSchema` also requires `idempotencyKey`. Supply a key through the existing UUID pattern and preserve it across retries of the same operation. Test double taps and network retries through the actual callable.
4. **Align marketplace queries with deployed indexes.** `DutyRepository.watchPublished` queries `status`, optional `specialtyName`, and descending `createdAt`. The committed duty indexes do not cover those query shapes. Add and deploy the exact required indexes and verify both unfiltered and specialty-filtered feeds in a disposable staging project. See [Firebase indexing guidance](https://firebase.google.com/docs/firestore/query-data/indexing).
5. **Remove the evidence approval race.** `recordVerificationDecision` reads evidence outside the transaction; pending evidence or a scanner rejection can race approval. Revalidate the evidence records and the applicable evidence set within the approval transaction, and restrict uploads to the intended lifecycle states. Pin reads/scans to the stored object generation. The existing comment claiming transactions cannot read collection queries should be checked against the installed Admin SDK. Add an upload/scan-versus-approval race test. See [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions).
6. **Finish the actual private-evidence pipeline.** `indexVerificationEvidence` only checks file signature, size and SHA-256. Valid-looking evidence remains `pending`; no trusted malware scanner is integrated. Configure the scanner, bucket, narrowly scoped service identity, quarantine/retention and official-source allowlist. Verify clean, infected, corrupt, duplicate-event and scanner-outage cases. Keep approval fail-closed until then. External provisioning is `BLOCKED_EXTERNAL` until confirmed.
7. **Make notification delivery recoverable.** Existing `outboxWorker.ts` is create-triggered only: marking an event `failed` does not schedule another attempt, expired leases have no recovery path, partial multicast failures are not inspected, and random inbox IDs do not deduplicate. Some producers address an organization ID as a user UID. Add bounded retry/lease recovery, deterministic inbox delivery and recipient resolution, and test process interruption plus partial FCM failure. These are existing dependencies newly exposed by real screens.
8. **Replace test labels with actual acceptance evidence.** `atomic_selection.test.ts` simulates a local counter; `security_rules.test.ts` evaluates local booleans. Neither proves actual selection transactions or Firestore authorization. Add real emulator callable/transaction tests for capacity, overlaps, duplicate applications, cross-tenant denial, verification decisions and audit atomicity. Replace the starter Flutter counter test with an application smoke test using injected Firebase dependencies. Earlier `TESTED` milestone labels must not imply production workflow proof.

### P1 — finish before a controlled pilot

- **Feedback privacy and duplicate protection.** Hospital reviews query by organization target, but the feedback rule only permits author/target UID/support access, not organization membership; the hospital query is denied. Align reads with the intended privacy model, never open all feedback globally. `submitFeedback` does check-then-random-write duplicate prevention; use a deterministic ID and atomic create/transaction. Add real authorization and concurrent-submission tests. Confirm subjective doctor ratings fit the constitution and approved product policy before displaying them.
- **Use canonical assignment data.** `HospitalRepository.watchOrgAssignments` reads `schedule`/`paymentTerms`, while the server writes `termsSnapshot`; time/payment values therefore fall back incorrectly. Doctor relative-time rendering accepts only Timestamp although verification callables can return other serialized forms. Map actual server fields without manufacturing current time or successful defaults.
- **Fix real hospital contact resolution.** Existing `getAssignmentContact` returns organization registration number as `phone`. Store and resolve an explicitly authorized contact field, retain the contact-grant check and audit, and test both parties' access.
- **Harden verifier identity and ownership checks.** The browser has a hardcoded username/password gate that merely launches Google sign-in; it is not an authentication factor. Remove that gate for release and use actual Firebase Auth plus claims/MFA. Current self-review prevention compares subject ID with verifier UID and does not detect a reviewer who owns/administers an organization. Add organization conflict-of-interest checks and test claim revocation and step-up expiry. Current recent-sign-in enforcement is not MFA proof.
- **Activate server enforcement for App Check after validation.** Android activates App Check, but no callable uses `enforceAppCheck` or an equivalent server check. Configure the browser provider too, verify valid Android/web requests first, and stage enforcement to avoid locking out reviewers. See [Firebase callable enforcement](https://firebase.google.com/docs/app-check/cloud-functions).
- **Make audit/state updates atomic and constrain boundary IDs.** Case creation/submission and organization creation have separate audit or multi-document writes. Bring critical state and audit into one transaction/batch. Validate document IDs and schedule ordering at server boundaries and enforce facility ownership. Keep contested application creation atomic; a deterministic path alone does not prevent parallel snapshot/outbox duplication.
- **Complete release setup and operations.** Validate client-owned signing, release AAB, SHA fingerprints, OTP/Google login, billing/bucket/Functions/Hosting, monitoring, backup restore, retention/deletion and rollback. Existing setup notes are historical; current cloud state was not reverified. Keep Phase 2 flags disabled and complete a consented pilot before wider rollout.
